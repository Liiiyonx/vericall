### 1.3 工程短板

1. `D:/VeriCall_data` 硬编码于：`server.py:43-49`、`pipeline.py:43`、`semantic_channel.py:53`、`acoustic_channel.py` demo、`voiceprint_channel.py` demo、`test_fusion_full.py:27-29`。

4. 演示强依赖 Ollama+GPU+D 盘数据，无降级。
5. 无 LICENSE / 单元测试 / CI。
6. 融合阈值 0.85/0.50/0.70 无实验依据；声纹阈值 0.55/0.35 同样拍脑袋。

10. **训练看板两处 bug**（`training_dashboard.html`）：`wdir` 变量未定义（L144，每次刷新必进 catch、状态恒显示"读取失败"、权重表永远空）；ETA 过滤条件 `!parts[0].includes('_')`（L129）把全部 epoch 文件排除，ETA 永不显示。
11. 前端 `innerHTML` 未转义用户输入（声纹名/文件名），本地低危但安全竞赛会被挑。
12. `.gitignore` 未覆盖 `data/history.jsonl`、`data/uploads/`、未来 `data/voiceprints/`——家人录音有误入库风险。

### 1.4 结论

**能参赛，且底子扎实**（真实 EER、三通道真实推理、可解释融合、赛事策略清晰，超过多数"PPT 项目"，进度已超前 README 里程碑的阶段一）。但现状是"技术 demo"而非"作品"：实时、中文场景、适老交互三大卖点均未落地。距 2027.03 约 6 个月，按本任务书执行可补齐。

**规则评分器设计**（新增 `src/fusion/rule_scorer.py`，约 80 行）：

```python
RULES = {
    "money_request":  ["转账", "汇款", "打钱", "安全账户", "垫付", "五万", "万块", "卡号", "二维码"],

# risk = 0.15*命中类别数 + 0.25*最高类别命中词数（封顶1.0）；命中0类 → normal/0.05
```

## 四、P1 · 核心叙事兑现（2026.09 下旬 – 11 月）

### P1-1 流式推理引擎（本任务书最重要的单项）

**目标**：把"整段文件分析"变成"边说边判"，端到端延迟 ≤2s/窗。

**为什么可行（基于现有代码的三个事实）**：
1. AASIST 输入 `nb_samp=48000` = **16kHz 下整 3 秒**——3s 滑窗与模型输入天然对齐，零改造。
2. 前端 `web/index.html` 已有 **WAV 录音器**（getUserMedia + 手写 WAV 编码），改造成 3s 分片上传即可，无需引入新前端依赖。
3. funasr 依赖里已有 **fsmn-vad**（SenseVoice 加载时就在用，见 `semantic_channel.py:122-123`），VAD 直接复用，不引入 webrtcvad。

**架构（新建 `src/server/`，4 个文件）**：

```
浏览器麦克风流 ──WS──▶ ingest.py ─▶ vad.py ─▶ window 3s/步进1s ─▶ scheduler.py
                                                                │ 串行依次跑
                                    ┌───────────────────────────┼──────────────┐
                                    ▼                           ▼              ▼
                              通道① AASIST                通道② CAMPPlus   通道③ ASR(累积转写)
                              (~0.1s/窗,常驻)             (~0.1s/窗,常驻)   (SenseVoice 常驻)
                                    └───────────┬───────────────┘              │
                                                ▼                              ▼
                                     incremental_fusion.py  ◀──── LLM 评分（节流：每5s或规则器触发）
                                     EMA平滑 + 状态机(绿→黄→红)               │
                                                ▼                              │
                                     ws_api.py → 前端实时变色/弹拦截 ◀──────────┘
```

**显存预算（RTX 5060 8GB，需冒烟实测确认）**：

| 常驻 | 显存（估） | 说明 |
|---|---|---|
| AASIST | ~0.3GB | 小模型，流式期间不卸载（省掉反复 load 的 3-5s） |
| CAMPPlus | ~0.3GB | 同上 |
| SenseVoice | ~2GB | 流式 ASR 必须常驻 |
| 流式 LLM | ~2-3GB | **换小模型**：qwen2.5:3b-instruct 或 deepseek-r1:1.5b |
| 合计 | ~5-6GB | 可行；r1:8b 明确不用于流式 |

**关键设计点**：

1. **双 LLM 策略**（写进答辩词）：实时线用小指令模型（qwen2.5:3b，响应 1-2s）；r1:8b 保留给"拦截后深度复盘报告"（不赶时间，分析质量高）。`semantic_channel.py` 顶部注释里你自己已预判了这一点。
2. **LLM 节流**：不是每窗都调 LLM。规则器（P0-4）每窗跑，命中 ≥0.5 或距上次 LLM ≥5s 才触发一次 LLM 对**累积转写**评分——延迟和算力都可控。
3. **增量融合算法**（`incremental_fusion.py` 核心，~100 行）：
   - 每通道分数 EMA 平滑：`s_t = 0.6·score_t + 0.4·s_{t-1}`（单窗误判不会瞬间翻转状态）；
   - 状态机带**迟滞**：绿→黄需连续 2 窗 fused≥0.5；黄→红需 fused≥0.7 或任一通道硬命中（score≥0.85 & conf≥0.6）；红→告警一次 + 10s 冷却（防反复轰炸老人）；连续 5 窗干净才降级；
   - 沿用 `FusionOrchestrator.decide()` 做每窗裁决（复用，不重写融合逻辑），状态机只消费其输出。
4. **WS 协议**（`ws_api.py`，挂到现有 FastAPI 上 `/ws/stream`）：
   - 客户端→服务端：二进制 WAV 分片（前端录音器每 3s 切一段，含 1s 重叠由服务端组装）；
   - 服务端→客户端 JSON 事件：
     ```json
     {"type":"window","idx":7,"t_rel":21.0,
      "channels":{"acoustic":{"score":0.91,"label":"spoof"},
                  "voiceprint":{"score":0.12,"label":"match"},
                  "semantic":{"score":0.83,"label":"money_request","transcript":"…急用五万…"}},
      "fused":0.74,"state":"YELLOW"}
     {"type":"alert","state":"RED","rationale":"…","advice":"建议挂断后回拨确认"}
     ```
5. **测试路径**：`scripts/test_streaming.py --replay 诈骗录音.wav` 回放文件流（无麦克风也能回归测试），输出时间线日志 + matplotlib 时间线图（每窗三通道分数/融合分/状态着色）——这张图直接进参赛 PPT。

**实施步骤**：① vad.py + 窗口组装（1天）→ ② scheduler 串行调度（复用现有 load→infer，改为常驻不卸载，1天）→ ③ incremental_fusion + 单测（1天）→ ④ ws_api + 前端改造（录音器分片 + 实时风险条，2天）→ ⑤ 回放测试与延迟测量（1天）。

**验收**：播放 60s 诈骗音频（前 30s 寒暄、后 30s 要钱），系统在进入要钱段 2 个窗内升级黄、4 个窗内红；每窗端到端延迟 P90 ≤2s；60s 正常家人闲聊全程绿（零误拦）。

### P1-4 电话信道仿真

**方案**：写 `scripts/degrade_audio.py`，预设档位：

```
--preset phone8k   : 重采样16k→8k→16k（去高低频）+ μ-law 压扩 + 轻度削顶
--preset mp3_16k   : ffmpeg 转 mp3 32kbps 再转回（模拟网络电话编解码）

```

### P1-5 融合阈值标定（把拍脑袋变成实验）

**方案**：
1. **构造场景集**：泛化 `test_fusion_full.py` 的选角逻辑为 `scripts/build_scenarios.py`——从 dev 协议抽 N=20 个"家人"说话人 ×（2 条 bonafide + 2 条 spoof）+ 20 个陌生人真声 = 100 条带期望标签的测试用例（期望：家人真声=allow、家人克隆=block、陌生人=block|caution）。
2. **跑全链路**：100 条 × 三通道真实推理，落盘每条的通道分数矩阵 `evaluation/scenario_scores.csv`（跑一次，后面扫阈值秒级完成，不用重跑模型）。
3. **非对称代价搜索**：
   - 代价定义：**误拦家人（FA）代价 = 3 × 漏放克隆（MISS）代价**（依据方案书"误把真儿子判为假货比漏报更伤产品"，系数做 1:1 / 3:1 / 1:3 敏感性分析三张表并列，让数据说话）；
   - 网格：hard_block ∈ [0.70, 0.95]×0.05，soft_alert ∈ [0.30, 0.60]×0.05，soft_block ∈ [0.50, 0.80]×0.05，三通道权重在单纯形上步长 0.05；
   - 输出：最优参数 + 等高线热力图（matplotlib）。
4. **消融实验（答辩王牌）**：去掉任一通道后的漏检率对比表——证明"三通道缺一不可"，这就是融合架构价值的直接证据。

**验收**：`evaluation/fusion_calibration.md` 含最优参数、代价曲线、消融表；`FusionOrchestrator` 默认参数更新为标定值并注明出处。
